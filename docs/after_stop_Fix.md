# After Stop Fix Field Notes

Date: 2026-07-07

Scope: documentation only. This note records the Phase 1 / Phase 1.1 stop-certificate status and known pipeline flags (FLAG-01 through FLAG-05) for field testing. It does not propose or apply code changes.

## Executive Verdict

Phase 1.1 stop-certificate validation can continue as a stop-only field test.

FLAG-01 does not block dry-run validation of:

```text
RPP drive -> stop certificate -> pivot -> alignment certificate -> next leg -> final DONE certificate
```

FLAG-01 does block or contaminate claims about the full production pipeline:

```text
DXF -> GPS_SURVEYED runtime placement -> runtime-entry path -> RPP -> spray binding -> paint output
```

So the correct judgement is:

```text
DOES NOT BLOCK STOP-ONLY
BLOCKS FULL PIPELINE ONLY
```

## Phase 1.1 Stop Fix Status

The stop-certificate work is a companion-side RPP hardening layer.

It is intended to prove physical transition safety:

- hard corner pivot requires a stop certificate
- hard corner next-segment tracking requires an alignment certificate
- run-boundary advance requiring alignment requires a stop certificate
- runtime-entry-to-MARK pivot requires a stop certificate
- final DONE requires a final stop certificate
- fresh moving telemetry must not certify stop or DONE
- stale fallback is still present, but must be visible as degraded evidence

This is not yet production-grade until field bags prove the behavior.

## Phase 1.1 Final Stop Certificate Rule

Final DONE must be certified by both:

```text
endpoint position tolerance
physical velocity settle
```

For precision stop certification, the final endpoint tolerance should be treated as:

```text
min(xy_goal_tolerance, corner_position_tolerance_m)
```

With the current precision defaults, that means:

```text
2 cm final certificate tolerance
```

Important hard rule:

```text
fresh stopped but 3 cm away from endpoint must not produce FinalStopCertificate
```

## FLAG-01: Staged Fingerprint Vs Runtime Path

FLAG-01 summary:

```text
The staged mission fingerprint can describe the staged waypoints and spray_flags,
while the actual runtime /path can be changed by GPS_SURVEYED placement and the
runtime-entry spray-OFF leg.
```

Observed risk:

- `/path/identity` may still publish the old staged fingerprint when publish verification is disabled.
- RPP recomputes the actual raw path hash internally.
- `/rpp/conditioned_path_identity` can prefer the old `/path/identity` fingerprint.
- Spray controller can compare conditioned geometry against the staged configured fingerprint.
- Result can be geometry mismatch or spray staying OFF.

## Does FLAG-01 Block Phase 1.1 Stop Testing?

No, not for stop-only testing.

RPP stop certificates are based on:

- the actual `/path` received by RPP
- the conditioned path generated by RPP
- current position
- measured velocity
- measured yaw rate
- heading error
- dwell timing

They are not certified from the staged fingerprint.

Therefore a dry-run stop-only test can still validate:

```text
stop -> pivot -> align -> final DONE
```

as long as the analysis uses the actual runtime path geometry, not the staged DXF fingerprint.

## What FLAG-01 Does Block

FLAG-01 blocks or invalidates claims about:

- spray binding correctness
- full DXF-to-spray production behavior
- GPS_SURVEYED runtime-entry identity correctness
- mission-config fingerprint integrity
- paint-on-field proof

It is mainly a full pipeline blocker, not a stop-certificate blocker.

## Runtime Entry Geometry And Stop Tests

Runtime-entry geometry can change the first actual path leg.

That does not automatically invalidate stop testing, but it changes what must be used as truth.

For stop-only validation, truth must be:

```text
actual /path
actual /rpp/conditioned_path
actual /rpp/stop_debug target N/E
actual /rpp/segment_debug run/segment state
```

Not:

```text
staged DXF waypoint list alone
```

If the test is meant to validate only stop behavior, runtime-entry geometry is acceptable only when the bag review explicitly measures against the runtime path.

## FLAG-03: Preview / Staged / Executed Geometry Truth Source

FLAG-03 status:

```text
PARTIAL RISK
```

This is not a confirmed staged-to-loaded execution bug.

Codex found that the staged mission path is consistent:

- `plan_and_stage` honors saved entity order, overrides, extensions, grouping, and spray flags.
- the staged artifact stores the final planned `waypoints` and `spray_flags`.
- `load_mission_to_controller` reads the staged artifact directly.
- no re-planning or re-alignment was found between staging and controller load.

The partial risk is on the client/operator preview side.

Earlier preview endpoints are not all executable truth:

```text
/entities  = entity-level DXF preview only
/segments  = planned LOCAL_NED segments, no GPS alignment
/align     = alignment sample, not final mission geometry
/plan-and-stage response = staged mission truth
/path/staged/{mission_id} = authoritative staged mission truth
```

Risk:

```text
The operator may visually confirm one preview, while the staged/executed mission uses the final grouped, extended, aligned, and spray-flagged geometry.
```

This is especially important for:

- GPS_SURVEYED aligned missions
- grouped line chains
- L-shapes
- closed shapes such as squares
- extension behavior
- spray flag visualization

Correct rule:

```text
After plan_and_stage, the client must render the staged mission artifact or the plan_and_stage returned merged_waypoints.
Do not treat /entities, /segments, or /align as final executable mission truth.
```

Impact on Phase 1.1 stop-only testing:

```text
DOES NOT BLOCK STOP-ONLY
```

A stop-only field test can continue if bag analysis uses:

```text
actual /path
actual /rpp/conditioned_path
actual /rpp/stop_debug
actual /rpp/segment_debug
```

Impact on full pipeline validation:

```text
PARTIAL FULL-PIPELINE RISK
```

Full DXF-to-drive/spray validation should not rely on early preview endpoints as proof of executed geometry. The authoritative comparison must be against the staged artifact and runtime `/path`.

## FLAG-04: Spray Degraded / OFF Mission Completion Risk

FLAG-04 status:

```text
PARTIAL RISK
```

This is a full pipeline spray-validation risk, not a Phase 1.1 stop-only blocker.

Codex found that continuous spray missions can load in a degraded state if spray mission config apply fails.

For continuous mode:

```text
spray_config_applied = false
spray_flags = all OFF
load_fingerprint = ""
mission can still start
mission can still drive
mission can still complete if RPP DONE + final spray OFF + rest/mode/disarm checks pass
```

This means a mission with MARK geometry can physically drive and finish while no spray occurred.

Dash and point are safer during load:

```text
dash config apply failure -> load fails closed
point config apply failure -> load fails closed
marked point dwell failure -> point execution fails
```

However, dash can still have a post-publish risk if the spray config applied successfully but conditioned path identity/hash binding later fails. In that case the rover may continue driving while the spray controller rejects the path and forces spray OFF.

Completion limitation:

```text
mission completion proves final spray OFF
mission completion does not prove MARK segments were sprayed
```

Impact on Phase 1.1 stop-only testing:

```text
DOES NOT BLOCK STOP-ONLY
```

Impact on full pipeline validation:

```text
BLOCKS FULL SPRAY SUCCESS CLAIMS
```

A full DXF-to-spray field result must not be called successful unless the bag proves spray binding and actual spray ON/OFF execution over MARK segments.

## FLAG-05: Stale Latched Path / Clear / Failed-Start Risk

FLAG-05 status:

```text
PARTIAL RISK
```

This is a drive-safety and mission-state risk.

Codex found that normal mission clear is safe:

```text
clear_mission_async
-> publish_path_clear()
-> empty /path
-> empty /path/identity
-> RPP clears internal path state
-> RPP publishes empty /rpp/conditioned_path
-> spray clears path model and forces OFF
```

So clear is the safest reset path.

However, stale geometry risk remains in these cases:

```text
failed start after mission /path was already published
stop/abort when current pose is unavailable
failed load that restores older resident mission state
manual/test path_publisher_node publishing /path directly
```

Important details:

- `/path` and `/path/identity` are reliable TRANSIENT_LOCAL, depth 1.
- `/rpp/conditioned_path` and `/rpp/conditioned_path_identity` are also transient-local.
- If an empty path is published, RPP clears correctly.
- If no clear/stop path is published, old geometry may remain latched or resident.
- `publish_stop_path` depends on current pose; if pose is unavailable, no stop path is sent.
- abort still attempts MANUAL/disarm, but stale path may remain latched if stop-path publish failed.
- `path_publisher_node` is not launched by production `rpp_start.sh`, but can override `/path` if manually launched or enabled with `publish_test_path=true`.

Impact on Phase 1.1 stop-only testing:

```text
PARTIAL SAFETY RISK
```

Phase 1.1 can continue, but each test should start from a known clean state:

```text
call clear_mission before loading
confirm empty /path or fresh mission /path
confirm /path/identity belongs to the current mission
confirm /rpp/conditioned_path_identity belongs to the current mission
do not run with path_publisher_node active
confirm pose is available before stop/abort testing
```

Impact on full pipeline validation:

```text
PARTIAL FULL-PIPELINE RISK
```

A full mission result should not be trusted if the bag shows stale `/path`, stale `/path/identity`, stale conditioned path, or a mission start failure after path publication without a later clear.
